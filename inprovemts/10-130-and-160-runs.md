# 130/s and 160/s with both autoscalers + 10 s webhook cooldown (2026-11-09)
Same setup as `09` (payment `dyn2`, orchestrator `dyn1`, fresh containers per run via `scripts/fresh.sh`, 5 s polling, 5 s simulator delay). Data: `data/dyn3-130`, `data/dyn3-160`.

| | 100/s (`09`) | 130/s | 160/s |
|---|---|---|---|
| offered / completed in run | 18,000 / 18,000 | 23,401 / 23,401 | 28,800 / 12,129 (16,671 pending at drain end; all sagas finished ~5 min later) |
| saga p50 / p95 / max | 6.2 / 10.9 / 24.0 s | 15.8 / 26.2 / 37.9 s | 59.4 / 172.3 / 183.0 s |
| peak RUNNING sagas | 705 (window) | 3,144 | 16,920 |
| webhook workers | 1->4 | 1->4 (5th at +150 s) | 1->4, 5th at +160 s, 6th ~+330 s |
| orchestrator pool | 10->15 | 10->20 | 10->40 (waits up to 150 ms avg/blocked) |
| payment pool | 10, no resize | 10, no resize (95% within 1 of cap, 254,902 blocked, 3.0 ms avg, 771 s total wait; max sample avg 4.6 ms < 5 ms trigger) | 10, no resize in the run (max sample avg 4.9 ms); first resize 10->15 at 19:57:06 after the run |
| orchestrator CPU container mean / max | 63 / 72% | 83 / 91% | 91 / 119% (host 67% mean, 84% max, 100 s > 70%) |
| payment / inventory / order CPU | 36 / 22 / 18% | 45 / 27 / 22% | 39 / 26 / 19% |
| DB probe latency | 4-10 ms | 4-10 ms | 4-9 ms (never rose; guard held once) |

130/s step intervals: capture-observed 13.8 s avg (was ~6 s), CREATE_ORDER 264 ms, 5a 1.3 s. 160/s: every orchestrator-driven step inflated (CREATE_ORDER p50 4.1 s / p95 61 s; MARK_ORDER_PAID 11.6 s; CONFIRM_STOCK 24 s).

Findings
- Capacity cliff between 100 and ~130/s on this staging stack: 130/s completes everything but at 2.4x p95; 160/s is overload (completion rate ~50-150/s vs 160 offered, backlog of 16,920 sagas).
- First choke: orchestrator (container ~1 core pinned at 160/s; host busy at 84%; its pool was grown to 40 and waits did not drop, so more connections did not help). Payment and the other services have CPU headroom. DB probe latency stayed flat, but Neon CPU was not measured.
- Second: payment DB pool at 10 is saturated from 130/s (95% full, ~4 goroutines waiting on average) and the workers' busy ratio (>1.0 per worker) includes that wait; its autoscaler did not act because its trigger needs avg wait >= 5 ms per blocked acquisition, but waits were many (255k) and short (3 ms). The trigger is blind to many short waits (total wait 771 s in 180 s).
- Worker scale-up late (5th worker at +150 s): scale-up requires backlog >= 10 and age >= 2 s, and by then the backlog has already drained at the cost of slow handling; utilisation (busy ratio) is not an up-trigger.
- Unexplained: 4b (attempt created -> capture observed) grew from ~6 s to 13.8 s at 130/s although gateway calls took 5-10 ms, webhook handler p95 was 23 ms and workers kept up. Not simulator CPU (11%). Needs a look at simulator delivery.
- No audit (phase 22) was run on these two runs.
