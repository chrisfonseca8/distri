distri - LOAD AND CORRECTNESS TESTING PLAN (cloud)
Written 2026-10-25. Nothing here has been run. Every number below is a plan or an
estimate, not a result. Prices are rough on-demand figures: check the AWS pricing
page for your region before launching anything.

======================================================================
0. GROUND RULES (from CLAUDE.md, apply to every test below)
======================================================================
- Change ONE main variable per run. No improvement claim without a comparable
  before/after run. Record each run in memory.md (plan.md section 12 template).
- Report ACCEPTED req/s and COMPLETED checkouts/s separately. A fast 202/200 with a
  growing backlog is not scaling. Say whether a number is peak or sustained.
- Everything goes through the gateway SIMULATOR. Never real Razorpay in a load test.
  Simulator throughput is labelled "simulated dependency" in every result.
- Webhooks: WEBHOOKS_DISABLED=true (simulator path) or a set secret. Never leave
  it unset (the payment service now fails closed).
- Neon free tier: 512 MB cap. Use a DISPOSABLE BRANCH, write down DB size before and
  after each run, delete test data after. Warm the compute up before measuring
  (it auto-suspends).
- Put EC2 in the SAME region as the Neon project (us-east-1 per the current URL).
  Cross-region latency would dominate every number (see reference metrics memory).
- Do NOT run `go run ./cmd/migrate` or integration tests with a .env that points at
  cloud. Pass DATABASE_TEST_URL explicitly (an incident on 2026-10-25 did this once).
- Stop or terminate every instance when a session ends. Set an AWS budget alert first.
- A learning deployment with single points of failure is not an HA deployment.

1. EC2 INSTANCES TO CREATE
======================================================================
Start small (Stage 1), grow only when a measurement says a box is the limit.

STAGE 1 - minimum useful setup (2 instances)
  #1 app-1        t3.medium (2 vCPU, 4 GB)     ~USD 0.042/h
       Docker Compose: orchestrator, order, inventory, payment services,
       gateway-simulator, RabbitMQ.  (Same layout as compose.local.yaml.)
       Why one box first: gives a baseline with the fewest moving parts.
  #2 loadgen-1    c6i.large (2 vCPU, 4 GB)     ~USD 0.085/h
       Runs testing/baseline/baseline.py and any other generator.
       Why separate: a load generator on the same box steals CPU from the
       system under test and invalidates the result.
  Database: Neon (existing project, disposable branch). No EC2 needed.
  Rough cost: ~USD 0.13/h  => about USD 1 per 8-hour session, plus EBS + transfer.

STAGE 2 - split the tiers (to find which tier limits throughput)
  #1 orchestrator   c6i.large       orchestrator-service only
  #2 order-inv      c6i.large       order-service + inventory-service
  #3 payment        c6i.large       payment-service (+ job workers)
  #4 broker         t3.medium       RabbitMQ only (memory/disk heavy, not CPU)
  #5 simulator      t3.small        gateway-simulator (so it never competes)
  #6 loadgen-1      c6i.large
  Rough cost: ~USD 0.45/h. Use for 2-3 hour sessions, then stop.

STAGE 3 - only if the load generator or one service proves to be the limit
  #7 loadgen-2      c6i.large       second generator (check loadgen CPU first;
                                    if loadgen CPU > 70% the numbers are suspect)
  #8 app replica    c6i.large       second replica of the hot service, behind nginx
  #9 nginx          t3.small        reverse proxy / load balancer (Phase G only)
  Replica tests need DB connection budget: replicas x DB_MAX_OPEN_CONNS must
  stay below the Neon connection limit.

OPTIONAL / LATER (discuss cost first)
  - Local Postgres on EC2 (e.g. m6i.large + gp3) to separate "Neon-limited" from
    "app-limited". Costs ~USD 0.10/h plus storage. Recommended AFTER the Neon baseline
    if DB latency looks like the limit.
  - Prometheus + Grafana on a t3.small (or use docker stats + pg_stat_statements
    only for the first runs).

Security group: ports open only between the instances and to your IP (SSH).
Nothing public except what a test needs. No credentials in AMIs or user-data;
.env files copied by hand and git-ignored.

    DB pool wait, service logs (alerts: relay AlertAttempts, transaction conflict).

======================================================================
3. WHAT TO TEST (points, in the order to run them)
======================================================================

--- A. BASELINE (first, one box, simulator healthy)
A1  Repeat baseline B0 on EC2: open-loop 50 arrivals in 60 s. Expect all COMPLETED.
    Compare to local B0 only as context (different hardware, DB far away).
A2  Single checkout latency breakdown (p50/p95/p99): HTTP accept, reserve, create
    order, payment, confirm, paid. Use the saga step timestamps.
A3  Idle system: CPU, memory, DB connections, outbox/relay polling cost at rest.

--- B. THROUGHPUT AND CAPACITY (find the knee)
B1  Step load: 10, 25, 50, 100, 200, 400 arrivals/s, 2 min each, uniform products.
    Record accepted/s, completed/s, p95/p99, error rate, backlog at the end.
B2  Find the knee: first step where completed/s stops following accepted/s or p99
    explodes. Name the limiting resource (CPU, DB pool, DB latency, RabbitMQ,
    simulator, loadgen).
B3  Sustained: hold 70% of the knee for 30 minutes. Backlog must stay flat.
B4  Burst: 5x the sustained rate for 30 s, then back. Measure time to drain
    (burst absorption is NOT sustained capacity).
B5  Open-loop vs closed-loop: same target rate with fixed-concurrency clients,
    to show the coordinated-omission difference.

--- C. CONTENTION AND CORRECTNESS UNDER LOAD
C1  Hot product: 100% of carts contain one product with stock 50, 500 attempts.
    Exactly 50 units sold, rest rejected cleanly, stock never negative,
    reserved <= on_hand at every sample.
C2  Uniform vs hot-product workload at the same rate: compare throughput, lock
    waits (log_lock_waits), deadlock count, 40P01 retries.
C3  Reversed multi-item carts concurrently (deadlock-safe lock ordering): zero
    unresolved deadlocks, retry count logged.
C4  Idempotency: same key repeated 1000x concurrently -> one saga, one order,
    one payment. Same key + different body -> rejected.
C5  Final reconciliation after every run (SQL): sum of stock movements = on_hand
    change; paid orders = succeeded payments = confirmed reservations;
    no order PAID without a succeeded payment; no reservation left RESERVED
    after all sagas finish; no duplicate refund; money totals match in paise.
C6  Large carts (20 lines, qty 100) and invalid inputs at rate: clean 4xx, no 5xx.

--- D. FAULT INJECTION UNDER LOAD (simulator controls)
D1  Gateway slow (latency 3-10 s): effect on payment window, ambiguous timeouts,
    reconciler load. No double charge.
D2  Gateway fails a % of payments (5, 20, 50): failed checkouts compensate
    (release stock), counts add up.
D3  Gateway lost response (charged but timeout): reconciler resolves; no blind retry.
D4  Gateway down (dial errors): ErrNotSent fast-fail path; recovery after it returns.
D5  Duplicate / out-of-order / delayed webhooks at rate: state stays monotonic.
D6  Refund path at volume: checkouts failing after payment are refunded exactly once.
D7  Bounded-wait paths: sagas stuck after payment refunded after
    SAGA_STUCK_REFUND_AFTER; stuck undo steps auto-revived 3x then left for a
    person (shorten the timers for the test, record them).
D8  Kill services mid-load, one at a time (orchestrator, order, inventory,
    payment): restart, confirm sagas resume, nothing lost or duplicated.
D9  RabbitMQ restart / stop for 60 s mid-load: outbox backlog grows, drains after,
    publisher confirms hold, nothing lost. (Do NOT recreate the container: data
    is keyed by hostname. Use restart, not recreate.)
D10 Postgres/Neon unavailable briefly (suspend or block egress): services recover,
    health checks flip, no stuck RUNNING sagas after recovery.
D11 Network delay between boxes (tc netem, Stage 2): saga timeouts, resend
    backoff, duplicate deliveries absorbed by idempotency.
D12 Dead-letter behaviour: poison message -> retry tiers -> dead queue;
    count dead messages before/after (baseline 379 pre-existing, do not purge).

--- E. QUEUES, WORKERS AND DB
E1  Worker concurrency sweep (payment WORKER_CONCURRENCY 1, 2, 4, 8, 16): one
    variable at a time. Before raising: check queue depth, oldest-job age, job
    duration, DB pool wait, CPU. Stop raising when DB or gateway saturates.
E2  Consumer prefetch / pool scaling (RabbitMQ consumer pool min/max): ready vs
    unacked, consumer utilisation, redeliveries.
E3  DB pool size sweep (DB_MAX_OPEN_CONNS per service): pool wait vs latency,
    total connections vs Neon limit.
E4  Outbox relay: batch size / poll interval vs publish lag (oldest unpublished
    age). Check relay alerts do not fire.
E5  Slowest queries under load: pg_stat_statements top 10 by total time; EXPLAIN
    the hot ones; check index use (idx_checkout_attempts_order_id, reservation
    indexes). Record before/after any index change.
E6  Lock waits and long transactions: pg_locks, log_lock_waits output, confirm no
    transaction spans an external call.
E7  Retention purge under load (outbox, processed_messages): table sizes stay
    bounded; purge does not hurt latency.

--- F. SCALING AND TOPOLOGY
F1  1 box vs split tiers (Stage 1 vs Stage 2), same load: which tier moved the
    knee.
F2  Replicas: 2 orchestrator replicas, then 2 payment replicas. Verify SKIP LOCKED
    claims, no duplicate step handling, no duplicate refund.
F3  GOMAXPROCS and CPU: CPU per service at the knee (worker concurrency vs DB
    connections vs CPU parallelism vs replicas are four separate knobs).
F4  Local Postgres vs Neon (optional): same test, to separate DB-limited from
    app-limited.

--- G. SOAK AND RESOURCE HEALTH
G1  2-4 hour soak at 50% of the knee: memory growth (leaks), goroutine count,
    connection count, outbox/table growth, disk, log volume, RabbitMQ memory.
G2  Slow-leak signals: p99 drift over time, GC pauses, file descriptors.
G3  Neon storage: size after soak and after cleanup (512 MB cap).

--- H. OPERATIONS CHECKS
H1  Admin tools on the cloud DB after fault runs: `admin stuck`, `review`,
    `parked`, `dead-jobs` show only expected items; revive works.
H2  Health endpoints and graceful shutdown (SIGTERM mid-load): in-flight work
    finishes or is recovered, no orphaned reservation after the sweeper runs.
H3  Orphan reservation sweeper: crash the orchestrator between reserve and saga
    creation at rate; reservations released, attempts closed, nothing live
    released.
H4  Restart recovery time: time from process start to normal throughput.
